## Learning goals

After this chapter, you can:

1. **Explain** the difference between iteration (a loop) and recursion (a function that calls itself).
2. **Identify** the base case and the recursive case in a recursive algorithm.
3. **Trace** a countdown and a factorial both ways, including the call stack for the recursive version.
4. **Spot** a missing or wrong base case and explain what goes wrong.

## Key terms

| Term | Meaning (one line, plain words) |
|---|---|
| **Algorithm** | A finite, step-by-step set of clear instructions that solves a problem or completes a task. |
| **Iteration** | Repeating steps with a loop, such as `for` or `while`. |
| **Recursion** | Solving a problem by having a function call itself on a smaller version of the same problem. |
| **Function** | A named group of steps that can be used (called) again, like `COUNTDOWN(n)`. |
| **Base case** | The simplest case, where a recursive function stops calling itself and gives an answer directly. |
| **Recursive case** | The case where the function calls itself with a smaller input. |
| **Call stack** | The computer's list of function calls that have started but not finished yet. The newest call is on top. |
| **Stack overflow** | An error that happens when the call stack gets too big, for example when the base case is never reached. |
| **Factorial** | n! = n × (n − 1) × ... × 1. For example, 4! = 4 × 3 × 2 × 1 = 24. |

## 1.5.1 Why does this matter? (the problem)

Many algorithms need to repeat steps. In Chapter 1.2, FIND-MAX repeated "compare and maybe replace" for every number. In Chapter 1.4, bubble sort repeated whole passes. Both used **loops**.

But some problems are naturally made of **smaller versions of themselves**:

- 4! = 4 × 3!, and 3! = 3 × 2!, and so on.
- A folder on your computer can contain folders, which can contain more folders.

For problems like these, there is a second way to repeat work: **recursion**. Knowing both ways, and when each one is safer or clearer, is an important skill for every programmer.

## 1.5.2 The idea

**Iteration** repeats steps with a loop: do something, change a value, check again.

**Recursion** solves a problem by solving a smaller version of the same problem first, until the problem is so small that the answer is obvious.

**Everyday analogy: Russian nesting dolls.** To find the smallest doll, you open the doll in your hands.

- If there is a smaller doll inside, you do **the same thing again** with that smaller doll. (recursive case)
- If the doll does not open, you have found the smallest one. Stop. (base case)

You could also find the smallest doll iteratively: "while the doll opens, take out the next doll". Same result, different way of thinking.

**Where the analogy stops working:** with real dolls, you can put each outer doll down and forget about it. A computer cannot forget. Every call that has not finished yet must be remembered on the **call stack**, so the computer can come back to it later. This uses memory, and if there are too many unfinished calls, the program crashes with a **stack overflow**.

## 1.5.3 How it works, step by step

We use the same pseudocode style as Chapters 1.1 to 1.4. `print` means "show this on the screen".

### 1.5.3.1 Iteration

A loop needs three things:

1. a **start value** (for example, `n` starts at 3),
2. a **question** that decides whether to repeat (`while n > 0`),
3. a **change** inside the loop, so the question can eventually be answered No (`n ← n - 1`).

This is the same idea as `i ← i + 1` in FIND-MAX (Chapter 1.2): without the change, the loop never ends.

### 1.5.3.2 Recursion

A recursive function needs two parts:

1. a **base case**: a simple input where the function gives the answer directly, without calling itself;
2. a **recursive case**: the function calls itself with a **smaller** input, which brings it one step closer to the base case.

If either part is missing or wrong, the function never stops calling itself.

### 1.5.3.3 The call stack

When a function calls itself, the first call does not finish yet. It **waits** for the new call to finish. The computer keeps all waiting calls on the **call stack**, like a pile of plates:

- each new call is put **on top**;
- the call on top is the one running now;
- when it finishes, it is taken **off the top**, and the call below it continues.

The last call to start is the first to finish. This is exactly how a stack works (see Chapter 2.3, Stacks and queues).

## 1.5.4 Worked example 1: countdown (both ways)

The task: count down from n to 1, then print "Liftoff!".

**Iteration:**

```
COUNTDOWN-LOOP(n)
    while n > 0
        print n
        n ← n - 1
    print "Liftoff!"
```

| Round | n at the check | Is n > 0? | Printed |
|---|---|---|---|
| 1 | 3 | Yes | 3 |
| 2 | 2 | Yes | 2 |
| 3 | 1 | Yes | 1 |
| 4 | 0 | No, leave the loop | Liftoff! |

**Recursion:**

```
COUNTDOWN(n)
    if n = 0
        print "Liftoff!"
    else
        print n
        COUNTDOWN(n - 1)
```

Each call is written one step further to the right. This shows the call stack growing:

```
COUNTDOWN(3)            prints 3, then calls COUNTDOWN(2)
  COUNTDOWN(2)          prints 2, then calls COUNTDOWN(1)
    COUNTDOWN(1)        prints 1, then calls COUNTDOWN(0)
      COUNTDOWN(0)      base case: prints "Liftoff!"
      COUNTDOWN(0)      finishes
    COUNTDOWN(1)        finishes
  COUNTDOWN(2)          finishes
COUNTDOWN(3)            finishes
```

| Step | Call stack (top on the right) | Printed |
|---|---|---|
| 1 | COUNTDOWN(3) | 3 |
| 2 | COUNTDOWN(3), COUNTDOWN(2) | 2 |
| 3 | COUNTDOWN(3), COUNTDOWN(2), COUNTDOWN(1) | 1 |
| 4 | COUNTDOWN(3), COUNTDOWN(2), COUNTDOWN(1), COUNTDOWN(0) | Liftoff! |
| 5 to 8 | The calls finish one by one, newest first, until the stack is empty | |

Both versions print **3, 2, 1, Liftoff!**. The loop changes `n` inside one running function. The recursive version starts a **new call** for each smaller `n`, and at its biggest moment it has 4 calls waiting on the stack.

**What if someone calls it with n = −1?**

| Version | What happens | Why |
|---|---|---|
| `COUNTDOWN-LOOP(-1)` | Prints only "Liftoff!" and stops | The first check, −1 > 0, is No, so the loop body never runs |
| `COUNTDOWN(-1)` | Never stops: −1, −2, −3, ... until the program crashes with a **stack overflow** | The base case only checks `n = 0`, and n only gets smaller, so it never reaches 0 |

A safer base case is `if n ≤ 0`. It catches every input that should stop, not just one exact value.

## 1.5.5 Worked example 2: factorial (both ways)

The task: work out n! = n × (n − 1) × ... × 1. For example, 4! = 4 × 3 × 2 × 1 = 24.

**Iteration:**

```
FACTORIAL-LOOP(n)
    result ← 1
    for i ← 1 to n
        result ← result × i
    return result
```

**Trace for n = 4:**

| Round | i | Calculation | result after the round |
|---|---|---|---|
| Start | | | 1 |
| 1 | 1 | 1 × 1 | 1 |
| 2 | 2 | 1 × 2 | 2 |
| 3 | 3 | 2 × 3 | 6 |
| 4 | 4 | 6 × 4 | **24** |

The loop stops after round 4, because the next value of i (5) is past n = 4.

**Recursion:**

```
FACTORIAL(n)
    if n ≤ 1
        return 1
    else
        return n × FACTORIAL(n - 1)
```

The idea: 4! = 4 × 3!. So to work out FACTORIAL(4), the function asks for FACTORIAL(3) and **waits** for the answer.

**Trace for n = 4.** Going down, each call waits. Coming back up, each call finishes its multiplication:

```
FACTORIAL(4)        needs 4 × FACTORIAL(3), waits
  FACTORIAL(3)      needs 3 × FACTORIAL(2), waits
    FACTORIAL(2)    needs 2 × FACTORIAL(1), waits
      FACTORIAL(1)  base case (1 ≤ 1): returns 1
    FACTORIAL(2)    returns 2 × 1 = 2
  FACTORIAL(3)      returns 3 × 2 = 6
FACTORIAL(4)        returns 4 × 6 = 24
```

| Step | Call stack (top on the right) | What happens |
|---|---|---|
| 1 | F(4) | 4 ≤ 1? No. Call F(3) and wait |
| 2 | F(4), F(3) | 3 ≤ 1? No. Call F(2) and wait |
| 3 | F(4), F(3), F(2) | 2 ≤ 1? No. Call F(1) and wait |
| 4 | F(4), F(3), F(2), F(1) | 1 ≤ 1? Yes. Base case: return 1 |
| 5 | F(4), F(3), F(2) | F(2) returns 2 × 1 = 2 |
| 6 | F(4), F(3) | F(3) returns 3 × 2 = 6 |
| 7 | F(4) | F(4) returns 4 × 6 = **24** |

Both versions give **24**. Notice the big difference from the countdown: in factorial, the real work (the multiplying) happens **on the way back up**, while the stack shrinks. Each call cannot finish until the call above it has returned its answer.

**Iteration or recursion?**

| | Iteration (loop) | Recursion |
|---|---|---|
| How it repeats | One function, a value changes each round | A new call for each smaller problem |
| Memory | Very little, only a few values | One waiting call on the stack for each level |
| Risk | A loop that never ends if the value never changes | A stack overflow if the base case is missing or never reached |
| Easiest when | You simply repeat a step a known number of times | The problem is made of smaller copies of itself (factorial, folders inside folders) |

When you trace by hand, the loop is usually easier: it only goes forward once. Recursion has to go all the way down to the base case first, because each call needs the answer from the call above it, and then come back up again.

Every recursive algorithm in this chapter can also be written as a loop, and the answers are the same. Choosing one is about which is clearer and safer for the problem.

## 1.5.6 Common misunderstandings

| Mistake | Why it is wrong | Correct idea |
|---|---|---|
| "Recursion is just a loop with a different name." | A loop repeats inside one running function. Recursion starts a **new call** each time, and every unfinished call waits on the stack. | Same result, but a different mechanism, and recursion uses more memory. |
| A base case that only matches one exact value, like `if n = 0`. | If the input skips that value (for example n = −1), the function never stops (stack overflow). | Use a base case that catches every input that should stop, like `if n ≤ 0`. |
| Forgetting to make the input smaller, for example calling `COUNTDOWN(n)` instead of `COUNTDOWN(n - 1)`. | The function calls itself with the same problem again and again. | The recursive case must always move closer to the base case. |
| Tracing past the base case. While writing this chapter, the first trace of FACTORIAL(4) went down to FACTORIAL(0), because 0! = 1 is also a correct base case in maths. | The code says `if n ≤ 1`, so FACTORIAL(1) already returns 1 and never calls FACTORIAL(0). | Always check which base case the code actually uses. With `n ≤ 1`, FACTORIAL(4) makes 4 calls, not 5. |
| "The answer is ready when the last call is made." | In factorial, the deepest call only returns 1. The multiplying happens on the way back up. | Trace both directions: calls going down, return values coming back up. |

## 1.5.7 Learner activity: a call stack made of paper

**Goal:** see recursion work by building the call stack with your own hands.

**You need:** about 6 small pieces of paper or sticky notes, a pen.

This function adds up the numbers from 1 to n:

```
SUM(n)
    if n ≤ 0
        return 0
    else
        return n + SUM(n - 1)
```

**Task:**

1. Write `SUM(4) = 4 + SUM(3) = ?` on a note and put it on the table. This is the bottom of your call stack.
2. SUM(4) needs SUM(3), so write `SUM(3) = 3 + SUM(2) = ?` on a new note and put it **on top** of the first one.
3. Keep going until you reach the base case. On that note, write the answer directly.
4. Now go back up. Take the top note off. Write its answer onto the note below, finish that addition, and take that note off too. Repeat until the stack is empty.
5. **Record:** how many notes were on the pile at the highest point? What is SUM(4)?
6. Write SUM as a loop instead (hint: start with `total ← 0`). Trace it for n = 4. Do you get the same answer?
7. **Reflect:** which version was easier to follow? Which one needed more paper (memory)?

A sample answer is in section 1.5.9.

## 1.5.8 Check your understanding

1. **Trace.** What does `MYSTERY(3)` return? What is the largest number of calls on the stack at the same time?

```
MYSTERY(n)
    if n ≤ 0
        return 0
    else
        return 2 + MYSTERY(n - 1)
```

2. **Find the error.** What happens when you call `FACTORIAL-BROKEN(3)`? How would you fix it?

```
FACTORIAL-BROKEN(n)
    return n × FACTORIAL-BROKEN(n - 1)
```

3. **Choose and explain.** You need to count down from **1,000,000**. Which is safer, `COUNTDOWN-LOOP` or the recursive `COUNTDOWN`, and why?

## 1.5.9 Answers and explanations

### Activity (section 1.5.7): sample answer

**The paper call stack, going down** (each new note goes on top):

| Note | Written on it |
|---|---|
| 1 (bottom) | SUM(4) = 4 + SUM(3) = ? |
| 2 | SUM(3) = 3 + SUM(2) = ? |
| 3 | SUM(2) = 2 + SUM(1) = ? |
| 4 | SUM(1) = 1 + SUM(0) = ? |
| 5 (top) | SUM(0): 0 ≤ 0, base case, returns **0** |

**Coming back up** (take off the top note each time):

| Note taken off | Answer passed down |
|---|---|
| SUM(0) | 0 |
| SUM(1) | 1 + 0 = 1 |
| SUM(2) | 2 + 1 = 3 |
| SUM(3) | 3 + 3 = 6 |
| SUM(4) | 4 + 6 = **10** |

At the highest point there were **5 notes** on the pile. SUM(4) = **10**.

**As a loop:**

```
SUM-LOOP(n)
    total ← 0
    for i ← 1 to n
        total ← total + i
    return total
```

| Round | i | total after the round |
|---|---|---|
| Start | | 0 |
| 1 | 1 | 1 |
| 2 | 2 | 3 |
| 3 | 3 | 6 |
| 4 | 4 | **10** |

Same answer, 10. The loop needed only one "note" (the value of total), while the recursive version needed 5 notes at once. That is the extra memory that recursion uses.

### Question 1

**MYSTERY(3) returns 6. At most 4 calls are on the stack.**

```
MYSTERY(3)          needs 2 + MYSTERY(2), waits
  MYSTERY(2)        needs 2 + MYSTERY(1), waits
    MYSTERY(1)      needs 2 + MYSTERY(0), waits
      MYSTERY(0)    base case (0 ≤ 0): returns 0
    MYSTERY(1)      returns 2 + 0 = 2
  MYSTERY(2)        returns 2 + 2 = 4
MYSTERY(3)          returns 2 + 4 = 6
```

At the deepest point, MYSTERY(3), MYSTERY(2), MYSTERY(1) and MYSTERY(0) are all on the stack: 4 calls. MYSTERY(n) works out 2 × n by adding 2, n times.

### Question 2

**It has no base case, so it never stops.** FACTORIAL-BROKEN(3) calls FACTORIAL-BROKEN(2), which calls (1), then (0), then (−1), (−2), and so on. No call ever returns an answer, the call stack keeps growing, and the program crashes with a **stack overflow**.

**Fix:** add a base case before the recursive case:

```
FACTORIAL(n)
    if n ≤ 1
        return 1
    else
        return n × FACTORIAL(n - 1)
```

### Question 3

**The loop is safer.** The recursive countdown would start a new call for every number, so at its deepest point it would have about 1,000,000 calls waiting on the call stack at the same time. That uses a lot of memory and would very likely crash with a stack overflow. The loop is one function that only changes the value of n, so it uses the same small amount of memory however big n is.

## 1.5.10 Summary

- **Iteration** repeats steps with a loop. A loop needs a start value, a question, and a change that lets the question become No.
- **Recursion** solves a problem by calling itself on a smaller version of the same problem.
- Every recursive function needs a **base case** (stop and answer directly) and a **recursive case** (call itself with a smaller input).
- The computer keeps unfinished calls on the **call stack**. The newest call is on top and finishes first.
- A missing or unreachable base case causes a **stack overflow**. A base case like `n ≤ 0` is safer than `n = 0`.
- Both ways give the same answers. Loops use less memory and are easier to trace; recursion can be clearer for problems made of smaller copies of themselves.
