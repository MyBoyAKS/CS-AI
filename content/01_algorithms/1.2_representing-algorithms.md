## Learning goals

After this chapter, you can:

1. **Explain** the three common ways to write down an algorithm: natural language, pseudocode and flowcharts.
2. **Read** a flowchart and follow it step by step, including its decisions.
3. **Convert** a short algorithm from one form into another.
4. **Choose** the most suitable form for a situation and explain why.

## Key terms

| Term | Meaning (one line, plain words) |
|---|---|
| **Algorithm** | A finite, step-by-step set of clear instructions that solves a problem or completes a task. |
| **Representation** | The form we use to write an algorithm down so others can follow it. |
| **Natural language** | Writing the steps as normal sentences, like in a recipe. |
| **Pseudocode** | Writing the steps as short, code-like lines that are not tied to any real programming language. |
| **Flowchart** | A diagram that shows the steps as shapes connected by arrows. |
| **Decision** | A yes/no question that decides which step comes next. In a flowchart it is a diamond. |
| **Loop** | A group of steps that is repeated until a condition is met. In a flowchart it is an arrow that goes back up. |

## 1.2.1 Why does this matter? (the problem)

Imagine you cook instant noodles exactly the way you like them, and you want your roommate to make them the same way. You write down: "Cook the noodles, add some chilli if you want, and wait a bit."

Your roommate has questions. How much water? Do the noodles go in before or after the water boils? How long is "a bit"?

The idea in your head was clear, but the way you **wrote it down** was not. The same thing happens with algorithms. A good algorithm is useless if nobody can follow it. That is why we have different ways to **represent** an algorithm. Each way has its own strengths, and choosing the right one makes the steps clear for the person (or computer) who has to follow them.

## 1.2.2 The idea

An algorithm is an idea: a list of steps. To share that idea, we have to write it down in some form. That form is called a **representation**. The steps stay the same; only the way we show them changes.

**Everyday analogy: giving directions.** Suppose a friend asks how to get from the library to your apartment. You could:

- **tell them in sentences:** "Go out of the library, walk south, and turn left at the shop." (natural language)
- **give them a numbered list:** "1. Exit the library. 2. Walk south 200 m. 3. Turn left at the shop." (pseudocode)
- **draw them a map with arrows.** (flowchart)

The route is the same in all three. Only the way you show it is different.

**Where the analogy stops working:** a map lets you look anywhere you like, in any order. A flowchart does not. You must start at "Start" and follow the arrows one step at a time. Also, none of the three forms can be run by a computer directly. To run an algorithm, someone has to turn it into a **program** in a real programming language (see Chapter 1.1, "Algorithm vs. Program").

## 1.2.3 How it works, step by step

### 1.2.3.1 Natural language

You write the steps as normal sentences.

- **Good for:** quick explanations to people, recipes, instructions for a friend.
- **Problem:** sentences can be vague. "Wait a bit" or "add some salt" can mean different things to different people. This breaks **definiteness**, one of the properties of an algorithm from Chapter 1.1.

### 1.2.3.2 Pseudocode

You write one step per line, using a few simple keywords. Pseudocode is not a real programming language, so no computer runs it. It is written for people, but it is precise enough that a programmer can turn it into code easily.

We use the same style as Chapter 1.1:

| Pseudocode | Meaning |
|---|---|
| `if ... then` | Do the indented lines below only if the question is true |
| `else` | Otherwise, do these lines instead |
| `for i ← 2 to n` | Repeat the indented lines with i = 2, 3, 4, ... up to n |
| `while ...` | Keep repeating the indented lines as long as the question is true |
| `x ← 5` | Store the value 5 in x ("x becomes 5") |
| `return x` | Stop and give x as the output |

**Indentation** (the spaces at the start of a line) shows which lines belong inside an `if` or a loop.

### 1.2.3.3 Flowcharts

You draw the steps as shapes and connect them with arrows. Each shape has a meaning:

| Shape | In this chapter we draw it as | Meaning |
|---|---|---|
| Oval | `( Start )` | Where the algorithm starts or ends |
| Rectangle | `[ Boil water ]` | A step: something you do |
| Diamond | `< Want spicy? >` | A decision: a yes/no question with two arrows out |
| Parallelogram | `/ Input list /` | Input (information coming in) or output (the result going out) |
| Arrow | `-->` or `v` | The order: which step comes next |

**Rules for a correct flowchart:**

1. There is exactly one Start.
2. Every step has an arrow going out, except End.
3. Every diamond has exactly two arrows out, labelled **Yes** and **No**.
4. An arrow that goes back up to an earlier step makes a **loop**.

## 1.2.4 Worked example 1: making instant noodles (a decision)

The same algorithm in all three forms.

**Natural language:**

> Boil water and add the noodles. If you want it spicy, add chilli. Wait 3 minutes, then it is ready.

**Pseudocode:**

```
boil water
add noodles
if you want it spicy then
    add chilli
wait 3 minutes
serve the noodles
```

**Flowchart:**

```
          ( Start )
              |
              v
       [ Boil water ]
              |
              v
       [ Add noodles ]
              |
              v
       < Want spicy? > --Yes--> [ Add chilli ]
              |                       |
              No                      |
              |                       |
              v                       |
      [ Wait 3 minutes ] <------------+
              |
              v
           ( End )
```

**Follow it both ways** to check that it works:

| Path | Steps followed, in order |
|---|---|
| Answer **Yes** at the diamond | Start, Boil water, Add noodles, Want spicy? (Yes), Add chilli, Wait 3 minutes, End |
| Answer **No** at the diamond | Start, Boil water, Add noodles, Want spicy? (No), Wait 3 minutes, End |

Both paths reach End, so the algorithm always finishes (**finiteness**). Notice that the flowchart shows something the sentence hides: both paths join again at "Wait 3 minutes".

## 1.2.5 Worked example 2: FIND-MAX (a loop)

This is the FIND-MAX algorithm from Chapter 1.1: find the largest number in a list. This time the flowchart has a **loop**: an arrow that goes back up so the same steps can repeat.

`A[i]` means "the item at position i in list A". Position 1 is the first item.

**Natural language** (from Chapter 1.1):

> Set max to the first number in the list. For each remaining number, if it is greater than max, set max to that number. When every number has been checked, return max.

**Pseudocode** (from Chapter 1.1):

```
FIND-MAX(A)
    max ← A[1]
    for i ← 2 to length(A)
        if A[i] > max
            max ← A[i]
    return max
```

**Flowchart:**

```
              ( Start )
                  |
                  v
           / Input list A /
                  |
                  v
           [ max ← A[1] ]
                  |
                  v
              [ i ← 2 ]
                  |
                  v
   +-----> < i ≤ length(A)? > --No--> / Output max / --> ( End )
   |              |
   |             Yes
   |              |
   |              v
   |       < A[i] > max? > --Yes--> [ max ← A[i] ]
   |              |                       |
   |              No                      |
   |              |                       |
   |              v                       |
   |        [ i ← i + 1 ] <---------------+
   |              |
   +--------------+
```

The pseudocode line `for i ← 2 to length(A)` hides three things that the flowchart shows separately: start at `i ← 2`, check `i ≤ length(A)?` before each round, and add 1 with `i ← i + 1` after each round. The arrow on the left going back up is the loop.

**Trace with the list A = 5, 8, 3** (length 3):

| Step | Box in the flowchart | Values | Result | max after the step |
|---|---|---|---|---|
| 1 | `max ← A[1]` | A[1] = 5 | max becomes 5 | 5 |
| 2 | `i ← 2` | | i becomes 2 | 5 |
| 3 | `i ≤ length(A)?` | 2 ≤ 3 | Yes, go down | 5 |
| 4 | `A[i] > max?` | A[2] = 8, is 8 > 5? | Yes, go right | 5 |
| 5 | `max ← A[i]` | | max becomes 8 | 8 |
| 6 | `i ← i + 1` | | i becomes 3, loop back up | 8 |
| 7 | `i ≤ length(A)?` | 3 ≤ 3 | Yes, go down | 8 |
| 8 | `A[i] > max?` | A[3] = 3, is 3 > 8? | No, go down | 8 |
| 9 | `i ← i + 1` | | i becomes 4, loop back up | 8 |
| 10 | `i ≤ length(A)?` | 4 ≤ 3 | No, go right | 8 |
| 11 | `Output max` | | Output **8** | 8 |

The loop ran 2 times (for i = 2 and i = 3), once for each number after the first. The output 8 is correct: it is the largest of 5, 8 and 3. The loop stops because i grows by 1 each round and must pass length(A) at some point, so the algorithm is **finite**. Loops are explained in more detail in Chapter 1.5.

## 1.2.6 Common misunderstandings

| Mistake | Why it is wrong | Correct idea |
|---|---|---|
| "Pseudocode is a programming language." | No computer can run pseudocode. It has no fixed rules that a computer understands. | Pseudocode is written for people. A programmer turns it into a real program later (Chapter 1.1). |
| "Natural language is always clear enough." | Sentences can hide the order of steps. Example from writing this chapter: "I prepare my bag. If I have time, I buy an onigiri. If it is raining, I wear a raincoat." Read literally, you would buy the onigiri before putting on your raincoat. | Check the order step by step. A flowchart forces you to decide exactly what comes next. |
| "A diamond can have one arrow out (or three)." | A decision is a yes/no question, so there are always two possible answers. | Every diamond has exactly two arrows out: **Yes** and **No**. |
| "A loop just goes back up." | If nothing changes inside the loop, the question gets the same answer forever and the algorithm never stops. | Something inside the loop must change (like `i ← i + 1` in FIND-MAX), so the loop can end. This keeps the algorithm **finite**. |
| "Three forms means three different algorithms." | The steps and their order are the same. Only the way they are written changes. | One algorithm, three representations. |

## 1.2.7 Learner activity: my morning routine as a flowchart

**Goal:** practise turning sentences (natural language) into a flowchart with decisions, and check that every path works.

**You need:** paper and a pen. A friend for step 6.

**Task:**

1. Write your morning routine, from waking up to leaving home, in 5 to 8 short sentences. Include **at least one decision** (a sentence with "if").
2. Underline every "if". Each one will become a diamond.
3. Draw the flowchart with the shapes from section 1.2.3.3: an oval for Start and End, a rectangle for each action, a diamond for each decision with **Yes** and **No** arrows.
4. Check your flowchart against the 4 rules in section 1.2.3.3.
5. Count the paths. One decision gives 2 paths. Two decisions, one after the other, give 2 × 2 = 4 paths. Follow every path with your finger. Does each one reach End?
6. Give only your flowchart (not your sentences) to a friend. Can they follow it without asking you anything? Every question they ask shows a step that is not clear yet. Fix it.

**Record:** your sentences, your flowchart, the number of paths, and one thing you changed after step 4 or step 6.

A sample answer is in section 1.2.9.

## 1.2.8 Check your understanding

1. **Predict.** Use the FIND-MAX flowchart from section 1.2.5 with the list **9, 4, 6**. How many times do you land on the box `max ← A[i]`? What is the output?
2. **Convert.** Write this as pseudocode (in the style of section 1.2.3.2) and then as a flowchart: "If it is raining, take an umbrella. Otherwise, wear sunglasses. Then leave the house."
3. **Find the error.** This flowchart breaks one of the 4 rules in section 1.2.3.3. Which rule? Fix it **without removing the diamond**.

```
( Start ) --> [ Boil water ] --> < Is the water boiling? > --Yes--> [ Add noodles ] --> ( End )
```

## 1.2.9 Answers and explanations

### Activity (section 1.2.7): sample answer

This is the author's own morning routine.

**Sentences (first version):** "I tidy up my bed, prepare my clothes and take a shower. Then I prepare my bag with my daily essentials. If I have time, I buy an onigiri. If it is raining, I wear a raincoat, otherwise a hoodie."

**What changed after checking:** read literally, the first version buys the onigiri before putting on the raincoat. The weather decision was moved before the onigiri decision, and a "Get dressed" step was added after the shower.

**Flowchart:**

```
               ( Start: wake up )
                       |
                       v
                [ Tidy up bed ]
                       |
                       v
              [ Prepare clothes ]
                       |
                       v
               [ Take a shower ]
                       |
                       v
                [ Get dressed ]
                       |
                       v
     [ Prepare bag with daily essentials ]
                       |
                       v
               < Is it raining? > --Yes--> [ Wear raincoat ]
                       |                          |
                       No                         |
                       |                          |
                       v                          |
                [ Wear hoodie ]                   |
                       |                          |
                       v                          |
              < Do I have time? > <---------------+
                       |
                       +--Yes--> [ Buy an onigiri ]
                       |                 |
                       No                |
                       |                 |
                       v                 |
           ( End: leave for class ) <----+
```

**Paths:** 2 decisions, one after the other, so 2 × 2 = 4 paths. All 4 reach End.

| Raining? | Time? | Path after "Prepare bag" |
|---|---|---|
| Yes | Yes | Wear raincoat, buy an onigiri, leave |
| Yes | No | Wear raincoat, leave |
| No | Yes | Wear hoodie, buy an onigiri, leave |
| No | No | Wear hoodie, leave |

Your own routine will be different. It is correct if it follows the 4 rules in section 1.2.3.3 and every path reaches End.

### Question 1

**0 times. Output: 9.**

| i | Question | Answer | max |
|---|---|---|---|
| | `max ← A[1]` | | 9 |
| 2 | Is 2 ≤ 3? | Yes | 9 |
| 2 | Is A[2] = 4 > 9? | No | 9 |
| 3 | Is 3 ≤ 3? | Yes | 9 |
| 3 | Is A[3] = 6 > 9? | No | 9 |
| 4 | Is 4 ≤ 3? | No, output max | 9 |

The largest number is already first, so `max` is never replaced. The loop still runs 2 times, because the algorithm cannot know that 9 is the largest until it has checked every number.

### Question 2

**Pseudocode:**

```
if it is raining then
    take an umbrella
else
    wear sunglasses
leave the house
```

The indentation matters. "Leave the house" is not indented, so it happens after both choices. If it were indented under `else`, you would only leave the house on sunny days.

**Flowchart:**

```
          ( Start )
              |
              v
       < Is it raining? > --Yes--> [ Take an umbrella ]
              |                            |
              No                           |
              |                            |
              v                            |
       [ Wear sunglasses ]                 |
              |                            |
              v                            |
       [ Leave the house ] <---------------+
              |
              v
           ( End )
```

### Question 3

**Rule 3 is broken:** every diamond needs two arrows out, but this one only has **Yes**. The flowchart does not say what to do if the water is not boiling yet.

**Fix:** add a **No** arrow to a "Wait 1 minute" step that loops back to the question:

```
          ( Start )
              |
              v
       [ Boil water ]
              |
              v
  +--> < Is the water boiling? > --Yes--> [ Add noodles ] --> ( End )
  |           |
  |           No
  |           |
  |           v
  |    [ Wait 1 minute ]
  |           |
  +-----------+
```

This makes a loop. It ends because the water gets hotter every minute until it boils.

Removing the diamond completely also gives a flowchart that follows the rules, but then "Boil water" no longer says how long to wait, which is the vagueness problem from section 1.2.3.1.

## 1.2.10 Summary

- An algorithm can be written down in different forms, called **representations**. The steps stay the same.
- **Natural language** is easy to read, but it can be vague and can hide the order of steps.
- **Pseudocode** uses one step per line, a few keywords (`if`, `else`, `for`, `while`, `return`) and indentation. People read it; computers do not run it.
- A **flowchart** uses shapes: oval for start and end, rectangle for a step, diamond for a yes/no decision, parallelogram for input and output. Arrows show the order.
- Every diamond has two arrows out (Yes and No). An arrow back up makes a **loop**, and something inside the loop must change so that it can end.
